Trading Game — Scaling Architecture
Proposal for growing the candidate universe from 60 to ~1,500 companies
Proposed · not implemented Living document — edit this page directly whenever the design changes. Nothing on this page is committed code yet; ActorCriticPolicy in policy.jl still uses full self-attention. Every row in the table below is a real measurement on this machine's GPU; the calculator below it evaluates a regression fitted to those measurements, so it can answer "what about N=750?" without a new GPU run for every value.
Why the current design won't reach 1,500
ActorCriticPolicy's MultiHeadAttention runs full self-attention across every candidate — all N stocks plus the portfolio token attend to each other, an N×N cost. (Game v2 adds a cash token, so N+2 tokens; the N² scaling is unchanged. The measurements below were taken on the earlier 3-channel, N+1-token policy and have not been re-run.) At N=60 (today) that's cheap. Measured directly on this machine (RTX 5060 Ti, 16.7 GB VRAM, 15.57 GB usable) by running ActorCriticPolicy's actual forward + backward + optimizer step at every combination below:

Batch size can't rescue N=1,500 the way it did for StockSwingPredictor, because that model's cross-attention is one query against N peers (O(N)) — ActorCriticPolicy's is every candidate against every other (O(N²)). Fitting memory(N,B) = c₀ + c₁B + c₂NB + c₃N²B to these 13 points gives R² = 0.9999999 — essentially exact — which is itself evidence the N² term is the real driver, not measurement noise.
Current network architecture — game v3
What ActorCriticPolicy is today for --game-version 3 (BSE, 15-minute bars): 28,485 parameters. The macro GRU and the news inputs are switched off in v3 (the code stays; other versions still use them), and there are no separate cash or portfolio tokens: the six portfolio scalars (cash state included) are repeated beside every stock and enter the same fusion layer. Every stock goes through the same weights, so the model has no notion of which stock is which. Shapes below are per decision step; N is the candidate count and attention runs over N tokens.
The ReLU layer
v3 has one ReLU layer, the fusion layer in front of attention (the separate portfolio and cash encoders are gone). It is a fully connected layer: every input feeds every output through its own weight (each line below is one weight), each output unit adds a bias, and a ReLU max(0, x) keeps positive values and zeroes the rest. Each stock's 80 inputs are its own 70 returns and 4 state features plus the 6 portfolio scalars, which are the same for every stock at a given bar. The same weights serve every stock. The sketch draws only a handful of nodes — the real widths are in the caption — but the lines are the real connectivity.

Current vs. proposed attention pattern
Current — full self-attention O(N²)
Every candidate attends to every other candidate (and to the cash and portfolio tokens) directly
Proposed — anchors + cash + portfolio O(N·(K+2))
Each candidate cross-attends to K fixed anchor stocks + a cash token + a portfolio token (v3 has no macro token)
Revised 2026-09-29 — the original proposal pooled all N candidates into one mean-pooled "market pulse" token. That throws away exactly what made cross-attention worth using over mean-pool in StockSwingPredictor v1→v2 in the first place: every candidate ends up reading the same blurred average, with no selectivity. Fixed by cross-attending to a small fixed set of real anchor stocks (K of them — index/sector leaders, not a synthetic average) instead of a pooled token, and by splitting the previously-combined macro+portfolio token into two separate tokens so a candidate can learn to weight "broad market conditions" and "my own book state" independently rather than reading them pre-blended by a fixed linear combination. Still O(N·(K+2)) — K anchors plus the 2 fixed macro/portfolio tokens (3 under game v2, which adds a cash token), none of it scaling with N.

The O(N·K) fix alone doesn't get N=1,500 to batch 128–256 on this GPU — the linear-in-N term now dominates. At the calculator's own defaults (N=1,500, K=8, B=32): current design predicts 29.0 GB, proposed predicts 24.5 GB — a real ~16% reduction, but both still exceed this card's usable VRAM. Removing the N² attention term doesn't touch the c₂·N·B term (GRU encoding each candidate's own price history, one pass per candidate regardless of attention pattern) — solved for the fitted coefficients, that term alone caps the proposed design at N=1,500 to roughly B≈11 verified-safe, B≈20 before the usable ceiling — nowhere near 256. Reaching GPU-scale batch sizes at N=1,500 needs a second lever on top of this proposal: a smaller per-candidate embed_dim, mixed precision, or gradient-checkpointing the GRU.
The model predicts final resident memory, not peak transient memory during backprop — treat anything above ~9 GB as needing real verification, not a guarantee. N=1,500/B=16 was measured to OOM, yet the fitted model predicts only ~14.5 GB for that exact point — well under the 15.57 GB usable ceiling. Backprop through attention briefly holds more memory than the steady-state figure this regression fits. Open questions
Which K stocks are anchors? Candidates: index constituents (e.g. Nifty 50), top-K by market cap, or one per major sector for spread. Whatever's chosen must be a subset of the episode's own candidate universe (so its embedding is already computed — no extra encoding pass) and should be stable enough episode-to-episode that the policy isn't relearning "who the anchors are" constantly. K is adjustable in the calculator above; default shown there is 8.
Are anchors picked once per episode, or re-selected per step? Fixed per episode is simplest and keeps K genuinely constant for the O(N·(K+2)) accounting; re-selecting (e.g. today's top movers) could be more informative but reopens a small O(N) selection cost each step and makes the attended set non-stationary within an episode.
Macro/portfolio token split — encoder architecture. Two small independent encoders (reusing the existing macro GRU + a portfolio Dense, just not concatenated before projection) is the obvious default; hasn't been checked for whether either token alone still carries enough signal once they can no longer lean on each other.
GPU wiring is a separate, still-needed piece of work. ppo.jl/train.jl run entirely on CPU today (a deliberate Stage 3 scoping decision) — the measurements above test the network in isolation, not the full rollout+update loop.
assemble_observation is a separate CPU bottleneck. It's a per-candidate Julia loop, called once per environment step — not addressed by any of the above. Worth profiling once N grows.

Revision log
2026-09-29
Dropped the pooled "market pulse" token; split macro from portfolio
Questioned during review: pooling all N candidates into one mean-pooled token throws away the selectivity that motivated cross-attention over mean-pool in the first place (same reasoning as StockSwingPredictor's v1→v2 move) — every candidate would've read the same blurred average. Replaced with cross-attention to a small fixed set of K real anchor stocks (index/sector leaders — their embeddings are already computed as part of the N candidates, no extra pooling pass). Separately, split the previously-combined macro+portfolio token (concatenated then passed through one shared Dense layer) into two independent tokens, so a candidate's attention can weight "broad market conditions" and "my own book state" differently instead of reading them pre-blended by a fixed linear combination. Cost is still O(N·(K+2)) — none of it scales with N. Updated the diagrams, pipeline, capacity calculator (K now means "anchor stocks"; formula uses N·(K+2)), and open questions accordingly. Also surfaced while re-testing the calculator against this change: the fix only removes the N² term — at N=1,500 the linear c₂·N·B term (GRU cost, one pass per candidate) already dominates, capping the proposed design's real batch size at N=1,500 to ~11–20, not the 128–256 the initial entry below hoped for. Added a callout above the chart making this explicit rather than letting the calculator imply the proposal alone solves GPU-scale batching at N=1,500.

2026-09-29
Initial proposal
Measured that the current full-self-attention ActorCriticPolicy OOMs on this machine's 16.7 GB GPU between batch 8 and 16 at N=1,500. Proposed replacing candidate-to-candidate self-attention with candidate-to-summary-token cross-attention (O(N·K) instead of O(N²)) to unlock GPU-scale batch sizes at 1,500 candidates, mirroring StockSwingPredictor's existing cross-attention pattern.
